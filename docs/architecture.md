# Архитектура MLOps-системы для прогнозирования отказов оборудования

## 1. Общее описание

Система проектируется как ML-система уровня зрелости 2 для задачи predictive maintenance. Её назначение — прогнозировать риск отказа оборудования по сенсорным данным и поддерживать надёжный production-жизненный цикл ML-модели.

Архитектура поддерживает:

- загрузку данных;
- валидацию данных;
- построение признаков;
- повторное использование признаков через Feature Store;
- обучение моделей;
- управление экспериментами;
- регистрацию моделей;
- проверку качества модели;
- production-сервинг модели;
- технический мониторинг;
- мониторинг качества модели;
- мониторинг drift данных;
- переобучение;
- замену модели в эксплуатации.

## 2. Бизнес-контекст

Незапланированные отказы оборудования приводят к простою производства, прямым финансовым потерям и нарушению SLA.

Система помогает команде эксплуатации заранее выявлять оборудование с высоким риском отказа и принимать решение о профилактическом обслуживании.

Основная бизнес-метрика — снижение незапланированного времени простоя оборудования.

## 3. ML-постановка задачи

Задача формулируется как бинарная классификация:

- отрицательный класс: нормальная работа оборудования;
- положительный класс: риск отказа оборудования.

Главный приоритет качества модели — `recall` по классу отказа. Ложноотрицательная ошибка означает, что реальный отказ не был предсказан, и оборудование может выйти из строя без профилактического обслуживания.

Также контролируется `precision`, потому что слишком большое количество ложных предупреждений увеличивает стоимость обслуживания.

## 4. Высокоуровневая архитектура

```text
Сырые сенсорные данные
    ↓
PostgreSQL: raw-таблицы
    ↓
Airflow: валидация данных и построение признаков
    ↓
Feast Feature Store
    ├── Offline Store: PostgreSQL
    └── Online Store: Redis
    ↓
Training pipeline
    ↓
MLflow Tracking и MLflow Model Registry
    ↓
Quality Gate
    ↓
Champion-модель
    ↓
FastAPI model serving
    ↓
Prometheus и Grafana monitoring
    ↓
Drift monitoring и quality monitoring
    ↓
Переобучение и замена модели
```

## 5. Компоненты системы

### 5.1 PostgreSQL

PostgreSQL используется как основное постоянное хранилище системы.

В PostgreSQL хранятся:

- сырые сенсорные данные;
- offline-таблицы признаков;
- логи предсказаний;
- результаты мониторинга качества модели;
- результаты мониторинга drift данных.

### 5.2 Feast Feature Store

Feast используется как Feature Store для централизованного управления признаками.

Feature Store содержит:

- сущность `machine`;
- feature views с сенсорными и эксплуатационными признаками;
- offline store на базе PostgreSQL;
- online store на базе Redis.

Использование Feast снижает риск training-serving skew, потому что одни и те же определения признаков применяются и при обучении модели, и при online-инференсе.

### 5.3 Redis

Redis используется как online-хранилище признаков. Он обеспечивает быстрый доступ к последним материализованным признакам при online-инференсе.

### 5.4 Airflow

Airflow используется как оркестратор ML-пайплайна.

Основной DAG включает следующие шаги:

1. извлечение данных;
2. валидация данных;
3. подготовка признаков;
4. применение определений Feast;
5. материализация online-признаков;
6. обучение моделей-кандидатов;
7. оценка моделей-кандидатов;
8. проверка модели через quality gate;
9. продвижение или отклонение модели.

### 5.5 MLflow

MLflow используется как система управления экспериментами и реестр моделей.

Для каждого запуска обучения логируются:

- параметры модели;
- метрики качества;
- артефакты модели;
- версия обучающего набора данных;
- отчёт об оценке качества.

MLflow Model Registry хранит версии моделей и поддерживает champion/challenger-подход.

### 5.6 Quality Gate

Quality gate предотвращает вывод в production модели, которая не соответствует требованиям качества.

Модель-кандидат может быть продвинута в production только при выполнении заранее заданных условий, например:

- `recall` по классу отказа не ниже установленного порога;
- `ROC-AUC` не хуже, чем у текущей champion-модели;
- `F1-score` находится на приемлемом уровне;
- inference latency удовлетворяет заданному SLO.

Если модель-кандидат не проходит quality gate, она отклоняется, а текущая champion-модель остаётся в эксплуатации.

### 5.7 FastAPI prediction service

FastAPI обслуживает текущую champion-модель.

Сервис предоставляет:

- `GET /health`;
- `POST /predict`;
- `GET /model/info`;
- `GET /metrics`.

Endpoint предсказания возвращает:

- вероятность отказа;
- предсказанный класс;
- уровень риска;
- рекомендуемое действие;
- версию активной модели.

### 5.8 Prometheus и Grafana

Prometheus собирает технические и сервисные метрики:

- количество запросов;
- latency;
- error rate;
- количество предсказаний;
- распределение предсказанных уровней риска.

Grafana используется для визуализации собранных метрик.

### 5.9 Мониторинг и запуск переобучения

Мониторинг выполняется на трёх уровнях:

- технические метрики;
- модельные метрики;
- бизнес-метрики.

Если мониторинг выявляет деградацию качества модели, drift данных или нарушение SLO, запускается переобучение. Новая модель сравнивается с текущей champion-моделью и продвигается только после прохождения quality gate.

## 6. CI/CD

GitHub Actions используется для CI/CD.

CI-пайплайн проверяет:

- unit-тесты;
- API-тесты;
- качество кода;
- сборку Docker-образа.

CD-этап обновляет сервис на облачной VM через Docker Compose.

## 7. Infrastructure as Code

Docker Compose используется как основной инструмент Infrastructure as Code в рамках проекта.

Он описывает следующие сервисы:

- API-сервис;
- PostgreSQL;
- Redis;
- MLflow;
- Airflow webserver;
- Airflow scheduler;
- Prometheus;
- Grafana.

Каждый production-сервис должен иметь healthcheck. Развернутый API должен предоставлять работающий endpoint `/health` со статусом HTTP 200.

## 8. Логика замены модели

Production-модель рассматривается как champion-модель. Новая обученная модель рассматривается как challenger-модель.

Challenger заменяет champion только если:

1. проходит offline-пороги качества;
2. не нарушает требования по latency;
3. улучшает или сохраняет основные метрики качества;
4. решение о promotion логируется в MLflow.

Если текущая champion-модель деградирует в эксплуатации, она выводится из активного сервинга через переключение сервиса на новую валидированную champion-модель.
