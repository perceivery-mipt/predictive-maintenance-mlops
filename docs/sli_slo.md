# SLI/SLO для MLOps-системы прогнозирования отказов оборудования

## 1. Назначение документа

Документ фиксирует ключевые SLI и SLO для ML-системы predictive maintenance. Система прогнозирует риск отказа оборудования по сенсорным данным и используется для поддержки решений о профилактическом обслуживании.

SLI используются для измерения фактического состояния системы, а SLO задают целевые уровни качества. Метрики разделены на три уровня:

- технический уровень;
- модельный уровень;
- бизнес-уровень.

Такое разделение необходимо, потому что корректная работа ML-системы определяется не только доступностью API, но и качеством модели, стабильностью данных и достижением бизнес-эффекта.

## 2. Технические SLI/SLO

Технические метрики описывают работоспособность production-сервисов: API, Feature Store, MLflow, Airflow, PostgreSQL, Redis, Prometheus и Grafana.

| Компонент | SLI | SLO | Критический уровень | Действие при нарушении |
|---|---|---|---|---|
| FastAPI inference service | Доступность `/health` | HTTP 200 не менее 99% времени | `/health` недоступен более 5 минут | Перезапуск сервиса, проверка логов, rollback последнего деплоя |
| FastAPI inference service | p95 latency endpoint `/predict` | p95 latency ≤ 300 мс | p95 latency > 500 мс в течение 15 минут | Проверка нагрузки, Redis, модели и инфраструктуры |
| FastAPI inference service | Error rate | Доля 5xx ошибок ≤ 1% | Error rate > 2% в течение 10 минут | Проверка логов API, зависимостей и входных данных |
| PostgreSQL | Доступность соединения | Соединение доступно не менее 99% времени | Нет соединения более 5 минут | Проверка контейнера, диска, credentials и healthcheck |
| Redis | Доступность online store | Redis отвечает не менее 99% времени | Redis недоступен более 5 минут | Перезапуск Redis, повторная materialization признаков |
| Airflow | Успешность DAG-запусков | Не менее 95% успешных запусков DAG | Два подряд неуспешных запуска retraining DAG | Анализ failed task, повторный запуск DAG |
| MLflow | Доступность tracking server | MLflow UI/API доступны не менее 99% времени | MLflow недоступен более 10 минут | Проверка контейнера, backend store и artifact store |
| Prometheus | Сбор метрик | Scrape success ≥ 99% | Метрики API не собираются более 10 минут | Проверка Prometheus targets и `/metrics` |

## 3. Модельные SLI/SLO

Модельные метрики описывают качество prediction service и устойчивость модели к изменению данных.

| Область | SLI | SLO | Критический уровень | Действие при нарушении |
|---|---|---|---|---|
| Качество классификации | Recall по классу отказа | Recall ≥ 0.80 | Recall < 0.75 на новой размеченной выборке | Запуск retraining DAG, запрет promotion слабой модели |
| Качество классификации | ROC-AUC | ROC-AUC ≥ 0.85 | ROC-AUC < 0.80 | Анализ данных, переобучение модели, сравнение champion/challenger |
| Качество классификации | F1-score по классу отказа | F1 ≥ 0.60 | F1 < 0.50 | Подбор порога классификации, переобучение |
| Ошибки модели | False Negative Rate | FNR ≤ 20% | FNR > 25% | Пересмотр threshold, усиление recall, retraining |
| Drift данных | PSI по ключевым числовым признакам | PSI < 0.20 | PSI ≥ 0.25 хотя бы по одному ключевому признаку | Drift investigation, retraining, обновление feature pipeline |
| Drift предсказаний | Изменение доли high-risk прогнозов | Отклонение не более 30% от baseline | Резкий рост/падение более 50% | Проверка данных, модели, порогов и feature store |
| Training-serving skew | Согласованность признаков training/inference | Нет несовпадений схемы признаков | Ошибка схемы или отсутствующий признак | Остановка promotion, исправление Feast definitions |

Главная модельная метрика — recall по классу отказа. В задаче predictive maintenance пропуск реального отказа потенциально приводит к простою оборудования, поэтому false negative является наиболее дорогой ошибкой.

## 4. Бизнесовые SLI/SLO

Бизнесовые метрики показывают, приносит ли ML-система ценность эксплуатации оборудования.

| Бизнес-цель | SLI | SLO | Критический уровень | Действие при нарушении |
|---|---|---|---|---|
| Снижение простоев | Доля незапланированного downtime | Снижение не менее чем на 10% относительно baseline | Downtime не снижается в течение периода наблюдения | Анализ качества модели и процесса maintenance |
| Раннее обнаружение отказов | Доля отказов, предсказанных заранее | Не менее 70% отказов имеют предупреждение до события | Менее 60% отказов были предсказаны заранее | Повышение recall, пересмотр горизонта прогнозирования |
| Контроль стоимости обслуживания | Доля ложных предупреждений | Не более 35% предупреждений являются ложными | Более 50% ложных предупреждений | Корректировка threshold, баланс precision/recall |
| Операционная применимость | Доля прогнозов, обработанных maintenance-командой | Не менее 90% high-risk прогнозов рассмотрены | Менее 80% рассмотрены | Проверка интеграции с процессом эксплуатации |

## 5. Quality Gate для продвижения модели

Новая модель рассматривается как challenger. Текущая production-модель рассматривается как champion.

Challenger может заменить champion только при выполнении следующих условий:

| Условие | Требование |
|---|---|
| Recall по классу отказа | Не ниже 0.80 и не хуже champion более чем на 2 п.п. |
| ROC-AUC | Не ниже 0.85 и не хуже champion |
| F1-score | Не ниже 0.60 |
| p95 latency | Не выше 300 мс |
| Схема признаков | Полностью соответствует Feast feature definitions |
| Интеграционные тесты API | Успешно пройдены |

Если хотя бы одно условие не выполнено, модель не продвигается в production. Она остаётся в статусе rejected/challenger, а текущая champion-модель продолжает обслуживать запросы.

## 6. Условия вывода модели из эксплуатации

Production-модель должна быть выведена из эксплуатации и заменена новой валидированной моделью, если выполняется хотя бы одно из условий:

- recall по классу отказа на новой размеченной выборке ниже 0.75;
- ROC-AUC ниже 0.80;
- PSI по ключевым признакам не ниже 0.25;
- p95 latency endpoint `/predict` выше 500 мс в течение 15 минут;
- error rate выше 2% в течение 10 минут;
- нарушена схема признаков между Feast и inference service.

Вывод модели из эксплуатации выполняется не прямым удалением модели, а переключением production-сервиса на новую champion-модель, которая прошла quality gate.

## 7. Мониторинг и реакция системы

Мониторинг выполняется непрерывно для технических метрик и периодически для модельных и бизнесовых метрик.

- Prometheus собирает технические метрики API и инфраструктуры.
- Grafana визуализирует latency, error rate, request count и распределение прогнозов.
- Airflow запускает регулярные задачи проверки качества и drift.
- MLflow хранит результаты обучения, оценки и promotion-решения.

При нарушении SLO система должна инициировать один из сценариев:

1. технический инцидент — перезапуск сервиса, rollback или проверка инфраструктуры;
2. деградация модели — запуск retraining DAG;
3. drift данных — анализ источников данных и переобучение;
4. ухудшение бизнес-метрик — пересмотр threshold, метрик качества и процесса использования прогнозов.

## 8. Связь SLI/SLO с архитектурой

SLI/SLO покрывают все ключевые компоненты архитектуры уровня 2:

- FastAPI отвечает за production-инференс;
- Feast отвечает за согласованность признаков;
- PostgreSQL и Redis отвечают за хранение offline- и online-признаков;
- Airflow отвечает за автоматизацию pipeline;
- MLflow отвечает за управление экспериментами и версиями моделей;
- Prometheus и Grafana отвечают за мониторинг;
- quality gate отвечает за безопасную замену модели.

Таким образом, система контролируется на техническом, модельном и бизнесовом уровнях, а решение о переобучении или замене модели принимается на основе измеримых метрик.
