# ADR-0001: Выбор задачи predictive maintenance

## Статус

Принято.

## Контекст

В рамках итоговой работы необходимо спроектировать ML-систему, которая демонстрирует воспроизводимый жизненный цикл модели: от очистки данных и обучения до регистрации модели, проверки качества, мониторинга и безопасного переключения inference-сервиса между версиями.

Для проекта нужна бизнес-задача, которая одновременно удовлетворяет нескольким требованиям:

- имеет понятный бизнес-смысл;
- допускает использование открытого датасета;
- может быть решена простой и воспроизводимой ML-моделью;
- хорошо демонстрирует необходимость MLOps-компонентов: Feature Store, оркестратора, реестра моделей, мониторинга, quality gate и canary deployment;
- позволяет определить технические, модельные и бизнесовые SLI/SLO.

Рассматривались следующие варианты:

1. прогнозирование оттока клиентов банка;
2. прогнозирование качества продукции;
3. классификация обращений в техническую поддержку;
4. прогнозирование отказов оборудования.

## Решение

Для работы выбрана задача predictive maintenance: прогнозирование отказов промышленного оборудования по сенсорным и эксплуатационным признакам.

ML-задача формулируется как бинарная классификация:

- `0` — нормальная работа оборудования;
- `1` — риск отказа оборудования.

В качестве открытого источника данных используется AI4I 2020 Predictive Maintenance Dataset. Датасет содержит признаки работы оборудования, такие как температура воздуха, температура процесса, скорость вращения, крутящий момент, износ инструмента и тип оборудования. Целевая переменная отражает факт отказа оборудования.

## Обоснование

Задача predictive maintenance хорошо подходит для демонстрации заявленного уровня зрелости ML-системы 2 по следующим причинам.

Во-первых, бизнес-смысл задачи прозрачен: незапланированные отказы оборудования приводят к простою производства, финансовым потерям и нарушению SLA. Система прогнозирования отказов позволяет заранее выявлять рискованные объекты и планировать профилактическое обслуживание.

Во-вторых, задача естественно требует мониторинга. Распределение сенсорных признаков может изменяться из-за смены режима эксплуатации, износа оборудования, сезонности или изменения производственной линии. Поэтому для системы важно отслеживать drift данных, качество модели и технические характеристики inference-сервиса.

В-третьих, задача хорошо связывает бизнес-метрики и ML-метрики. Бизнес-метрика — снижение незапланированного времени простоя оборудования. Основная ML-метрика — recall по классу отказа, потому что пропущенный отказ является более дорогой ошибкой, чем ложное предупреждение. Дополнительно контролируются precision, F1-score и ROC-AUC.

В-четвёртых, табличная структура данных позволяет сосредоточиться на проектировании и развертывании ML-системы, а не на сложной предобработке изображений, текстов или временных рядов.

## Последствия

Выбор задачи predictive maintenance определяет дальнейшую архитектуру проекта:

- сущностью Feature Store является оборудование (`machine`);
- в Feast описаны сенсорные и эксплуатационные признаки оборудования;
- offline source для Feast реализован на базе parquet-файла;
- online store для Feast реализован на базе Redis;
- модель предсказывает вероятность отказа оборудования;
- FastAPI-сервис возвращает вероятность отказа, класс риска и рекомендуемое действие;
- model quality gate ориентирован на recall по классу отказа, F1-score и ROC-AUC;
- latency контролируется отдельно как технический SLI/SLO inference-сервиса;
- мониторинг включает технические, модельные и бизнесовые SLI/SLO;
- drift-контроль реализован отдельным Evidently pipeline;
- retraining pipeline может быть повторно запущен при деградации качества, drift признаков или нарушении SLO;
- новая модель становится `champion` только после прохождения quality gate;
- canary gateway позволяет постепенно переключать traffic между stable и canary inference service и выполнять rollback при необходимости.

## Альтернативы

### Прогнозирование оттока клиентов банка

Преимущество варианта — простая и понятная табличная классификация. Недостаток — задача менее выразительно демонстрирует промышленный MLOps-контур, чем predictive maintenance.

### Прогнозирование качества продукции

Преимущество варианта — простота реализации. Недостаток — более слабая связь между ошибкой модели и операционными бизнес-последствиями.

### Классификация обращений в техническую поддержку

Преимущество варианта — интересная бизнес-постановка. Недостаток — необходимость работы с текстом, что увеличивает сложность проекта и может отвлечь от основной цели дисциплины: развертывания ML-моделей.

## Итог

Выбрана задача predictive maintenance, потому что она является достаточно простой для воспроизводимой реализации, но при этом хорошо демонстрирует промышленную мотивацию MLOps: мониторинг, переобучение, управление версиями моделей, quality gate, Model Registry и безопасное переключение production inference service через canary deployment.
