# ML-манифест проекта

## 1. Предыстория

Промышленное оборудование работает в условиях изменяющихся нагрузок, температуры, скорости вращения, износа инструмента и других эксплуатационных факторов. Незапланированный отказ оборудования приводит к простою производства, затратам на аварийный ремонт, нарушению SLA и потере выручки.

Заказчику требуется система, которая заранее оценивает риск отказа оборудования по сенсорным данным и помогает принимать решение о профилактическом обслуживании до наступления аварии.

## 2. Ценностное предложение

Проектируемая ML-система снижает риск незапланированного простоя оборудования за счёт раннего обнаружения потенциальных отказов.

Система создаёт ценность для бизнеса за счёт:

- раннего выявления оборудования с повышенным риском отказа;
- сокращения незапланированного downtime;
- перехода от реактивного ремонта к профилактическому обслуживанию;
- снижения затрат на аварийное восстановление;
- повышения прозрачности состояния оборудования через мониторинг технических, модельных и бизнес-метрик.

## 3. Цели

Ключевые цели проекта:

1. Построить воспроизводимый ML-пайплайн для задачи прогнозирования отказов оборудования.
2. Реализовать единое управление признаками через Feature Store.
3. Обеспечить обучение, оценку и регистрацию моделей через систему управления экспериментами.
4. Развернуть API-сервис для online-инференса.
5. Настроить мониторинг технических и модельных метрик.
6. Реализовать quality gate, который предотвращает вывод в эксплуатацию модели низкого качества.
7. Обеспечить возможность переобучения и замены production-модели при деградации качества.

## 4. Решение

Система проектируется как MLOps-система уровня зрелости 2.

Основной сценарий работы:

1. Сенсорные данные оборудования поступают в PostgreSQL.
2. Airflow запускает пайплайн валидации данных и построения признаков.
3. Feast управляет признаками и обеспечивает согласованность между training и serving.
4. Offline-признаки хранятся в PostgreSQL.
5. Online-признаки материализуются в Redis.
6. Training pipeline обучает модели-кандидаты.
7. MLflow логирует параметры, метрики и артефакты моделей.
8. Модель-кандидат сравнивается с текущей champion-моделью.
9. Quality gate принимает решение о promotion или rejection.
10. FastAPI обслуживает текущую champion-модель.
11. Prometheus и Grafana используются для мониторинга сервиса.
12. При деградации качества или обнаружении drift запускается переобучение.

В продукт входит:

- подготовка данных;
- Feature Store;
- обучение модели;
- оценка качества;
- MLflow Tracking и Model Registry;
- API-сервинг;
- мониторинг;
- quality gate;
- воспроизводимое развертывание через Docker Compose;
- CI/CD-проверки через GitHub Actions.

В продукт не входит:

- разработка пользовательского веб-интерфейса;
- промышленный Kubernetes-кластер;
- интеграция с реальными SCADA/IoT-системами;
- автоматическое принятие ремонтных решений без участия инженера.

## 5. Осуществимость

Решение осуществимо в рамках учебного проекта, потому что задача имеет табличную структуру, а все ключевые компоненты могут быть воспроизведены в Docker Compose.

Используемые ресурсы:

- открытый датасет для predictive maintenance;
- локальная разработка на Python;
- Docker Compose для инфраструктуры;
- PostgreSQL для хранения данных;
- Redis для online feature store;
- Feast для управления признаками;
- MLflow для управления экспериментами и моделями;
- Airflow для оркестрации;
- FastAPI для сервинга;
- Prometheus и Grafana для мониторинга;
- облачная VM для демонстрационного развертывания.

Основное ограничение проекта: система является учебно-промышленным прототипом. Она демонстрирует архитектуру и жизненный цикл ML-модели, но не подключается к реальному промышленному оборудованию.

## 6. Данные

В качестве обучающего набора данных используется открытый датасет для задачи predictive maintenance. Он содержит наблюдения по оборудованию и эксплуатационные признаки, такие как температура, скорость вращения, крутящий момент и износ инструмента.

Целевая переменная:

- `0` — нормальная работа оборудования;
- `1` — отказ или риск отказа оборудования.

Источники данных в системе:

- обучающий набор данных — открытый датасет predictive maintenance;
- production-like данные — новые записи, поступающие в PostgreSQL и имитирующие поток сенсорных наблюдений;
- логи предсказаний — результаты работы API-сервиса;
- данные обратной связи — новые размеченные наблюдения, которые используются для оценки качества production-модели.

Процесс разметки:

- в учебном датасете целевая переменная уже задана;
- в production-сценарии метка отказа появляется позднее, после фактического события отказа или подтверждения нормальной работы оборудования.

## 7. Метрики

Основная бизнес-метрика:

- снижение незапланированного времени простоя оборудования.

Дополнительные бизнес-метрики:

- доля предотвращённых отказов;
- доля оборудования высокого риска, проверенного до аварии;
- снижение числа аварийных ремонтов;
- снижение стоимости незапланированного обслуживания.

Основные ML-метрики:

- recall по классу отказа;
- precision по классу отказа;
- F1-score;
- ROC-AUC;
- false negative rate.

Технические метрики:

- latency API;
- p95 latency;
- error rate;
- uptime;
- CPU и memory usage;
- количество запросов к `/predict`.

## 8. Оценка качества модели

Offline-оценка качества выполняется на отложенной тестовой выборке.

Основной приоритет — recall по классу отказа. Это связано с тем, что пропуск реального отказа является наиболее дорогой ошибкой для бизнеса.

Дополнительно контролируются:

- precision, чтобы не создавать чрезмерное число ложных предупреждений;
- F1-score как баланс precision и recall;
- ROC-AUC как качество ранжирования объектов по риску;
- confusion matrix для анализа типов ошибок.

Online-оценка качества выполняется после появления новых размеченных данных и включает:

- recall по новым отказам;
- prediction drift;
- feature drift;
- долю объектов, отнесённых к high-risk;
- стабильность latency и error rate.

## 9. Подбор модели

Подбор модели выполняется итеративно.

Базовая модель:

- Logistic Regression.

Модели-кандидаты:

- Random Forest;
- Gradient Boosting;
- CatBoost или XGBoost при необходимости.

Итеративный подход:

1. Обучить простую baseline-модель.
2. Зафиксировать baseline-метрики в MLflow.
3. Обучить несколько моделей-кандидатов.
4. Сравнить качество моделей по recall, F1 и ROC-AUC.
5. Выбрать модель-кандидат, которая проходит quality gate.
6. Зарегистрировать модель в MLflow Model Registry.
7. Продвинуть модель в champion только при выполнении требований качества.

## 10. Инференс

Система выполняет online-инференс через FastAPI.

Пользователь или внешняя система отправляет параметры оборудования в endpoint `/predict`. Сервис возвращает:

- вероятность отказа;
- предсказанный класс;
- уровень риска;
- рекомендуемое действие;
- версию активной модели.

Дополнительно допускается batch-инференс для периодического анализа всего парка оборудования, но основной сценарий проекта — online API-сервинг.

## 11. Обратная связь

Источники обратной связи:

- фактические события отказа оборудования;
- подтверждение нормальной работы оборудования;
- логи предсказаний API;
- данные мониторинга latency и error rate;
- данные мониторинга drift признаков;
- качество модели на новых размеченных данных.

Обратная связь используется для:

- оценки production-модели;
- обнаружения деградации качества;
- запуска переобучения;
- принятия решения о замене champion-модели.

MDD используется: да.

Архитектурные решения принимаются на основе метрик, статистических тестов и ADR-документов. Для анализа latency используется сравнение распределений времени отклика существующей и улучшенной системы, формулирование гипотез H0/H1, выбор статистического теста, p-value и фиксация решения в ADR.

## 12. Управление проектом

Для реализации учебно-промышленного прототипа требуется следующая команда:

- ML Engineer — подготовка данных, обучение моделей, MLflow;
- MLOps Engineer — Docker Compose, Airflow, Feast, CI/CD;
- Backend Engineer — FastAPI inference service;
- Data Engineer — PostgreSQL, пайплайны данных, feature store;
- DevOps Engineer — облачное развертывание и мониторинг.

В рамках индивидуальной работы роли совмещаются одним исполнителем.

Ожидаемые результаты:

- GitHub/GitLab-репозиторий с кодом и документацией;
- работающий API-сервис в облаке;
- Docker Compose-инфраструктура;
- MLflow Tracking и Model Registry;
- Airflow DAG для жизненного цикла модели;
- Feast Feature Store;
- Prometheus/Grafana monitoring;
- документы: ML-манифест, архитектура, SLI/SLO, ADR по MDD.

Ориентировочные этапы:

1. Проектирование архитектуры и документации.
2. Подготовка данных и baseline-модели.
3. Реализация Feature Store.
4. Реализация MLflow и training pipeline.
5. Реализация FastAPI inference service.
6. Реализация Airflow DAG.
7. Реализация мониторинга.
8. Подготовка ADR и SLI/SLO.
9. Облачное развертывание.
10. Подготовка к устной защите.
