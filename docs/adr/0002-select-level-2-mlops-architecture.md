# ADR-0002: Выбор архитектуры ML-системы уровня 2

## Статус

Принято.

## Контекст

Итоговая работа требует спроектировать ML-систему, которая обслуживает полный жизненный цикл модели: от очистки данных, подачи данных в необученную модель и обучения до вывода модели, не соответствующей метрикам качества, из эксплуатации через переключение трафика на новую обученную модель.

Для максимального уровня зрелости требуется система уровня 2. Такая система должна включать:

- версионирование кода;
- CI/CD-пайплайн;
- Feature Store;
- сервинг модели через API;
- мониторинг качества предсказаний;
- систему управления экспериментами;
- оркестратор.

Кроме того, система должна быть воспроизводимо развернута и иметь работающий облачный сервис с endpoint `/health`.

## Решение

Для проекта выбрана архитектура ML-системы уровня 2 со следующими компонентами:

- GitHub — версионирование исходного кода;
- GitHub Actions — CI/CD;
- Docker Compose — Infrastructure as Code и воспроизводимое развертывание;
- PostgreSQL — хранение raw-данных, offline-признаков, логов предсказаний и мониторинговых таблиц;
- Feast — Feature Store;
- Redis — online store для Feast;
- Airflow — оркестратор ML-пайплайнов;
- MLflow — experiment tracking и model registry;
- FastAPI — сервис online-инференса;
- Prometheus — сбор технических и сервисных метрик;
- Grafana — визуализация метрик;
- quality gate — правило продвижения модели из challenger в champion.

Высокоуровневый поток данных и моделей:

```text
Raw sensor data
    ↓
PostgreSQL
    ↓
Airflow: validation + feature engineering
    ↓
Feast Feature Store
    ├── Offline Store: PostgreSQL
    └── Online Store: Redis
    ↓
Training pipeline
    ↓
MLflow Tracking + Model Registry
    ↓
Quality Gate
    ↓
Champion model
    ↓
FastAPI prediction service
    ↓
Prometheus + Grafana monitoring
    ↓
Drift / quality monitoring
    ↓
Retraining and model replacement
```

## Обоснование

Выбранная архитектура соответствует уровню зрелости 2, потому что покрывает не только обучение модели, но и production-эксплуатацию.

### Feature Store

Feast выбран как Feature Store, потому что он позволяет централизованно описывать признаки и использовать одни и те же feature definitions для обучения и online-инференса. Это снижает риск training-serving skew.

Offline store реализуется на PostgreSQL, потому что исторические признаки нужны для обучения и анализа качества модели. Online store реализуется на Redis, потому что inference-сервису нужен быстрый доступ к актуальным признакам.

### Оркестратор

Airflow выбран как оркестратор, потому что жизненный цикл модели состоит из последовательности зависимых шагов: загрузка данных, валидация, построение признаков, материализация признаков, обучение модели, оценка, проверка quality gate и promotion.

### Управление экспериментами и реестр моделей

MLflow используется как система управления экспериментами и реестр моделей. Это позволяет сохранять параметры обучения, метрики, артефакты и версии моделей. В рамках проекта используется champion/challenger-подход: текущая production-модель является champion, новая обученная модель является challenger.

### Сервинг

FastAPI выбран для online-сервинга модели. Сервис предоставляет endpoints `/health`, `/predict`, `/model/info` и `/metrics`. Это позволяет проверить работоспособность сервиса, получить прогноз, узнать активную версию модели и собрать метрики.

### Мониторинг

Prometheus и Grafana используются для мониторинга технических и сервисных метрик. Дополнительно в проекте фиксируются модельные метрики и drift признаков. Это необходимо для принятия решения о переобучении модели и замене production-версии.

### Infrastructure as Code

Docker Compose выбран как основной инструмент Infrastructure as Code. Он позволяет воспроизводимо поднять все компоненты системы в едином контуре: API, PostgreSQL, Redis, MLflow, Airflow, Prometheus и Grafana.

Kubernetes не выбран как обязательная часть основной реализации, потому что для целей итоговой работы важнее обеспечить стабильную работу полного MLOps-контура. При этом архитектура допускает дальнейшую миграцию inference-сервиса в Kubernetes для масштабирования, rolling update и rollback.

## Quality Gate

Модель-кандидат может быть продвинута в production только при выполнении условий:

- recall по классу отказа не ниже установленного порога;
- ROC-AUC не хуже текущей champion-модели;
- F1-score находится на приемлемом уровне;
- latency инференса не нарушает SLO;
- решение о promotion зафиксировано в MLflow.

Если модель-кандидат не проходит quality gate, она отклоняется, а текущая champion-модель остаётся активной.

## Последствия

Принятое решение определяет структуру проекта:

- `app/` содержит FastAPI-сервис;
- `dags/` содержит DAG-файлы Airflow;
- `pipelines/` содержит скрипты подготовки данных, обучения, оценки и продвижения модели;
- `feature_repo/` содержит Feast-репозиторий;
- `infra/` содержит Docker Compose и конфигурации мониторинга;
- `docs/` содержит архитектуру, манифест, SLI/SLO и ADR-документы.

Система становится сложнее, чем простой ML-скрипт, но зато демонстрирует полный production-жизненный цикл модели.

## Альтернативы

### Только FastAPI + модель в pickle-файле

Этот вариант проще, но не соответствует уровню 2, потому что не содержит Feature Store, оркестратора, реестра моделей и полноценного мониторинга.

### Docker Compose без Feast

Этот вариант позволил бы развернуть сервис, но не закрыл бы требование Feature Store и не решал бы проблему согласованности признаков между обучением и inference.

### Kubernetes как основной контур

Kubernetes ближе к промышленному deployment, но для данной работы повышает инфраструктурную сложность и риск нестабильного результата. Поэтому основной контур реализуется через Docker Compose, а Kubernetes рассматривается как возможное дальнейшее развитие.

## Итог

Выбрана архитектура ML-системы уровня 2 на базе Feast, Airflow, MLflow, FastAPI, Prometheus/Grafana, PostgreSQL, Redis, GitHub Actions и Docker Compose. Архитектура покрывает полный жизненный цикл модели и поддерживает управляемую замену production-модели через quality gate.
